Если клиенту нужен логин и пароль, подключение к прокси идёт по TLS на
отдельном слушателе. Адрес и порт показаны в шапке панели состояния;
TLS-слушатель включает проверку логина, HTTP-слушатель логин не принимает.

## Когда это нужно

Логин прокси — отдельная учётная запись, создаваемая в разделе «Аккаунты»
через «Новый логин прокси». Его назначают клиенту; тогда source-адреса
связываются с точным username. Это полезно, когда несколько клиентов
сидят за одним NAT-адресом и IP их не различает, или когда нужна
персональная идентификация. Успешная аутентификация не открывает доступ
сама по себе: политику определяет клиент.

## Доверие сертификату прокси

Клиент должен доверять issuer серверного сертификата прокси. Корневой CA
добавляется в системное хранилище доверенных корней:

- **Linux:** `/usr/local/share/ca-certificates/kraken-proxy.crt`, затем
  `sudo update-ca-certificates`.
- **Windows:** `certutil -addstore -f "ROOT" kraken-proxy.crt`.
- **macOS:** добавить в «Связку ключей» и отметить доверенным.

Раздавать приватный ключ нельзя. Без доверия сертификату клиент откажется
от подключения; обходить проверку (`curl -k`, `verify_peer false`)
нельзя — это небезопасная инструкция.

## Логин и пароль в URL прокси

Клиента настраивают на адрес:

```
https://<user>@<kraken-host>:<port>
```

Логин указывается в userinfo URL, пароль клиент запрашивает отдельно
(Basic-промпт или переменная окружения) и передаёт только внутри
установленного TLS-соединения. Не вставляйте пароль в URL: он попадёт в
логи, историю shell и конфиги.

Пример для curl:

```
curl --proxy 'https://<user>@<kraken-host>:<port>' https://example.com
```

Пример для переменных окружения (утилиты, поддерживающие userinfo):

```
export https_proxy="https://<user>@<kraken-host>:<port>"
```

## Почему пароль только через TLS

Basic-аутентификация передаёт пароль в открытом виде. Без TLS пароль
виден в сети и доступен перехвату, поэтому Kraken принимает логин
только на TLS-слушателе: plaintext для auth-клиентов запрещён, а
отсутствие или ошибка credentials не пропускают трафик. Серверное
TLS-доверие продолжает проверяться клиентом — это отдельный слой от
аутентификации.

## Защитные запреты

Защитные destination/port deny выполняются до аутентификации: закрытые
адреса и опасные порты не открываются логином. IP/CIDR и точный username
совместно выбирают политику. См.
[Закрыто по умолчанию и защитные запреты](help:how-default-deny).
