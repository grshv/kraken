# Модель угроз

## Активы и границы доверия

Защищаются: исходящий доступ и изоляция клиентов, политика, пароли и сессии,
Docker-хост, серверные TLS-ключи, аудит и сведения о внутренних ресурсах.

Границы: браузер → HTTPS панели → модуль применения → Squid → интернет; отдельно
клиент → Squid, панель → SQLite и tmpfs, Squid → ключ прокси. Модуль применения
работает в процессе панели и границей не является.

## Угрозы и меры

| Угроза | Мера | Проверка |
| --- | --- | --- |
| Открытый прокси | Публикация на заданный адрес, deny-all по умолчанию, клиенты по source IP | Неизвестный источник получает отказ (`TestSmoke`, `TestFlows`) |
| Обход прокси прямым egress | Firewall на границе сети, включая IPv6 и UDP/443 | Вне продукта; описано в [deployment](../operations/deployment.md#сеть) |
| Доступ к внутренним адресам и metadata | Защитные запреты до правил клиентов, проверка разрешённого адреса, закрытые 6to4, Teredo, NAT64 | `TestNetwork`, в том числе DNS rebinding |
| Эксплойт панели меняет правила | Типизированная политика, allowlist expert-секции, нет shell API | Тесты валидатора; остаточный риск признаётся |
| Захват хоста через Docker | Нет socket, privileged, host PID и network | `TestBaseImage`: capabilities и `NoNewPrivs` |
| Expert-секция читает файлы или запускает процессы | Allowlist директив, запрет файлов-параметров, helpers, include, `sc_` | Тесты `policy`, `TestSmoke` |
| Squid читает секреты панели | Разные UID, БД и ключ панели недоступны Squid ([ADR 0009](../adr/0009-separate-squid-uid.md)) | `TestLayout`, `TestSmoke` (изоляция UID) |
| Подготовка тома меняет чужие файлы | Только каталог с раскладкой Kraken; посторонние имена, symlink, hard link — отказ без изменений; без `DAC_OVERRIDE`/`FOWNER` | `TestDeployRefusesForeignDirectory` |
| CA установки подписывает чужой сайт | Критичные name constraints, `pathlen 0`, ключ 0600 | Тесты `tlscert` |
| Подмена своего сертификата | `cert install` только из stdin: пара, срок, `serverAuth`, SAN; при ошибке файлы не меняются | Тесты `cmd/control`, `TestOpsCertReplace` |
| HSTS ломает соседние хосты | `max-age` без `includeSubDomains` и `preload` | Тест заголовков |
| Injection в конфиг | Строгая модель доменов и адресов, фиксированные argv | Фикстуры CRLF, метасимволов, путей |
| XSS из логов и справки | Текст без HTML, CSP `script-src 'self'`, стили — по хешам и nonce (`internal/csp`) | Тесты `csp`, vitest генератора хешей |
| CSRF и кража сессии | CSRF-токен, Origin, cookie `__Host-`, хеш токена в БД, список и завершение своих сессий | Тесты cross-origin и отзыва |
| Перебор пароля | Argon2id, лимиты входа и смены пароля, локальный bootstrap | Тесты throttle и смены пароля |
| Сбой применения расширяет доступ | Журнал и LKG в БД, `flock`, запуск Squid только после восстановления | Fault-тесты на каждой границе, `TestOpsForcedKill` |
| Заполненный диск | Пороги 512 и 64 MiB, ротация логов, сроки телеметрии | `TestOpsDiskFull`, тесты `507` |
| Утечка TLS-ключа | Права файлов, ключи вне образа и Git, не в логах | `TestOpsCertReplace`, `make scan-secrets` |
| Менеджер видит или меняет чужое | Фильтр области на сервере в каждом обработчике ([ADR 0007](../adr/0007-admin-and-manager-roles.md)) | Негативный тест на каждый запрет |
| Утечка через diff, поиск, ошибки | Менеджеру — структурный diff своей области, без squid.conf; ошибки без имён чужих объектов | Тесты ответов вне области |
| Подмена зависимостей | Lockfile, digest и SHA, подпись релиза Squid, attestations, SBOM, сканирование | CI `image`, `security`, `make scan` |
| Prompt injection | Логи, UI-строки и импортированные конфиги — данные, не инструкции | Ревью |

## Процессы и полномочия

- Squid (`proxy`) и панель (`kraken`) работают под разными UID. Squid читает свой
  конфиг, верификаторы включённых логинов прокси и пароль менеджера в tmpfs и ключ
  прокси, но не может их создать, заменить или удалить; БД и ключ панели ему
  недоступны. Панель в группе `proxy` читает логи Squid: обратной изоляции нет.
- Пароль менеджера Squid новый на каждый старт контейнера и не хранится на томе и в
  копиях. Reload и rotate возможны только с loopback на 3131; запросы с loopback не
  пишутся в access log.
- Root есть только у PID 1 (entrypoint, Pebble). Контейнер: `CHOWN`, `SETUID`,
  `SETGID`, `KILL`, `no-new-privileges`; у Squid и панели эффективных capabilities
  нет. CLI от root, кроме `entrypoint`, `squid-start` и `proxy-auth`, сбрасывает
  права до `kraken`.
- API Pebble в сеть не публикуется.

## Сеть

Панель доступна сети управления, прокси — сетям клиентов. Опубликованные порты
Docker проверяются снаружи: одного INPUT ufw недостаточно
([Docker packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/)).

## Остаточные риски

- IP идентифицирует источник запроса, а не человека. `CONNECT` на разрешённый порт
  может нести любой TCP-протокол.
- Root или администратор Docker на хосте обходит прикладные ограничения.
- Локальный аудит и телеметрия не защищены от изменения при компрометации панели
  или хоста.
- `cache_peer` в expert-секции или `upstream_proxy` меняют маршрут трафика;
  egress firewall остаётся обязательным.
- Обновление образа прерывает и панель, и прокси.

## Пароли

В SQLite только salted Argon2id verifier. Исходный пароль проходит через память при
вводе и проверке; гарантированное обнуление памяти Go не заявляется. Сброс,
смена своего пароля и создание сессии сверяют текущий hash в транзакции, поэтому
вход со старым паролем не переживает сброс. Подробно —
[authentication-and-certificates](authentication-and-certificates.md).
