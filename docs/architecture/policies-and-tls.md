# Политики клиентов и TLS

Как типизированный снимок превращается в правила Squid. Код — `internal/policy`.

## Клиент

Клиента определяет source IP, который видит Squid, и, для клиента с логином прокси,
этот логин. Обычно это адрес `/32` или `/128`; CIDR сети или группы означает доверие
всем её адресам. Тип host/network/group — подпись для UI.

- Сети включённых клиентов без логина не пересекаются; проверка идёт по разобранным
  сетям, а не по строкам. `/0` и неопределённые адреса запрещены.
- NAT, скрывающий клиентов за одним адресом, делает их неразличимыми; различать их
  можно логинами прокси.
- Общий серверный сертификат TLS-прокси не идентифицирует устройство.

## Модель

```text
Client: id, name, kind(host|network|group), source_networks[], enabled,
        access(list|all_web|none), tls_profile_id, proxy_username,
        policy_ids[], destinations[]
Policy: id, name, destinations[]
Destination: domain, include_subdomains
TLSProfile: mode(tunnel), proxy_transport(http|tls), cert_ref
```

Политика — именованный набор доменов без режима и подключения. Клиент подключает до
64 политик и держит до 1024 своих доменов, до 64 сетей.

- `list` — итоговый список: объединение своих доменов и политик
  (`policy.EffectiveDestinations`) без повторов и записей, покрытых `*.parent`.
  Пустой список — отказ во всём.
- `all_web` — внешние HTTP и HTTPS на разрешённых портах; списки сохраняются, но не
  действуют.
- `none` — клиент описан, всё закрыто.
- Защитные запреты и «запрещено для всех» действуют в любом режиме.

Домены — канонические ASCII-имена; IDN вводится в punycode. `*.example.org`
хранится как `example.org` с флагом поддоменов. CR/LF, пробелы, схемы URL,
userinfo, regex и IP-литералы отклоняются; разрешить IP списком доменов нельзя.

Снимок пишется в схеме 2. Снимок схемы 1 (`policy_id` у клиента, режим и TLS-профиль
у политики) переводится при чтении (`policy.Upgrade`): клиент берёт подключение и
режим своей прежней политики, политика-список остаётся набором, политика
«весь веб» исчезает. Так читаются старые черновики и ревизии без миграции БД.

## Порядок правил

1. Manager 3131: только GET с loopback к фиксированным отчётам и `reconfigure`,
   `rotate`; остальное на этом listener закрыто.
2. Canary 3130: любой запрос получает отказ; ответ несёт заголовок
   `X-Kraken-Revision` с отпечатком ревизии.
3. Запрет опасных портов; `CONNECT` — только на разрешённые порты.
4. Запрет manager Squid на клиентских listeners.
5. Запрет защищённых и, если не разрешены, частных адресов назначения.
6. «Запрещено для всех» (`sc_blocked_dst`).
7. Адреса клиентов с логином: на HTTP-listener — отказ `tls_required`, на TLS —
   только с действующим логином и generation.
8. Клиенты (или expert-секция): `all_web` либо один `dstdomain` ACL итогового
   списка; правило привязано к listener подключения клиента.
9. Финальный `http_access deny all`.

Каждый защитный и финальный запрет помечает транзакцию (`annotate_transaction`,
`sc_deny=<причина>`). Причины (`policy.DenyReasons`): `port`, `connect_port`,
`manager`, `protected`, `private`, `blocked`, `tls_required`, `no_rule`. Access log
пишется в формате `kraken` — родной `squid` плюс `%{sc_deny}note` («-», если отказ
не из этих правил, например из expert-секции). Поэтому отказ по адресу, в который
разрешился домен, виден как `protected` или `private` без повторного DNS-запроса.
Отказ проверки логина (407) не размечается.

## Порты

- Разрешённые порты по умолчанию: HTTP 80 и 443, `CONNECT` — 443.
- Никогда не разрешаются: 22, 23, 25, 110, 143, 465, 587, 993, 995, 9050, 9051.
  `all_web` этого не отменяет.
- Listener-порты 3128 и 3129 задаёт установка; 3130, 3131 и 8443 зарезервированы.
  `https_port` рендерится, когда есть сертификат и ключ прокси.

## Адреса назначения

Защищённые — закрыты всегда:
`0.0.0.0/8`, `127.0.0.0/8`, `169.254.0.0/16`, `224.0.0.0/4`, `240.0.0.0/4`,
`::/128`, `::1/128`, `fe80::/10`, `ff00::/8`, NAT64 `64:ff9b::/96` и
`64:ff9b:1::/48`, discard `100::/64`, Teredo `2001::/32`, 6to4 `2002::/16`.
6to4 и Teredo закрыты целиком: в них кодируются произвольные IPv4, включая
внутренние.

Частные — закрыты, пока не включён `allow_private_destinations`:
`10.0.0.0/8`, `100.64.0.0/10`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`,
`192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`,
`2001:db8::/32`, `fc00::/7`.

Squid 7 хранит IPv4 как IPv4-mapped IPv6 и сливает перекрывающиеся диапазоны в
`dst`, поэтому `::ffff:0:0/96` в списке совпал бы со всем IPv4. Этого диапазона в
списке нет: mapped-формы закрывают IPv4-записи (проверено `TestNetwork`).
Проверка `cache_peer` снимает mapped-форму сама.

Правила проверяют адрес, в который разрешилось имя, поэтому DNS rebinding на
внутренний адрес получает отказ. Это не заменяет egress firewall на хосте.

## Три слоя TLS

| Слой | Что шифруется | Сертификат |
| --- | --- | --- |
| HTTPS панели | Браузер → панель | Сертификат панели |
| TLS к прокси | Клиент → Squid (3129) | Сертификат прокси; клиент доверяет CA |
| HTTPS сайта | Клиент → сайт внутри `CONNECT` | Исходный сертификат сайта |

Подключение клиента — требование, а не подсказка: правило клиента с TLS привязано к
TLS-listener, и на HTTP-listener он получает отказ (клиент с логином —
`tls_required`). Для HTTPS сайтов известны source IP, host:port,
результат туннеля, длительность и байты; путь, HTTP-статус сайта и содержимое — нет.
HTTPS не кешируется ([ADR 0003](../adr/0003-tunnel-only-https.md)).

## Логины прокси

Клиент с `proxy_username` требует TLS-подключения и установленного сертификата
прокси. Логин сравнивается точно, с учётом регистра. Разные логины могут делить
адреса за NAT; пересечение клиента без логина с клиентом с логином или одинаковых
логинов запрещено. Защитные запреты срабатывают до проверки пароля. Helper и
generation ACL — [ADR 0008](../adr/0008-proxy-logins.md).

## Настройки

Settings задаёт разрешённые порты и порты `CONNECT`, память кеша и размер объекта,
DNS-серверы и TTL, таймауты, лимит тела запроса и число ротаций логов.

- `upstream_proxy` (`address`, `port`, `exclusive`) — вышестоящий прокси:
  `cache_peer <address> parent <port> 0 no-query no-digest default name=sc_upstream`,
  при `exclusive` ещё `never_direct allow all`; без него при недоступном peer Squid
  идёт напрямую. Адрес — IP-литерал вне защищённых сетей; частный адрес допустим:
  это выбор администратора, клиентам частные назначения он не открывает.
- `blocked_domains` — «запрещено для всех»: те же правила, что у доменов политики,
  до 1024; действует и для `all_web`, и в expert-режиме.
- `hide_client_address` — `forwarded_for delete` и `via off`: адрес клиента и версия
  прокси не уходят на сайты и вышестоящий прокси.

## Expert-секция

Expert-режим заменяет блок клиентов; защитные запреты и «запрещено для всех» идут
до него. Граница — [ADR 0004](../adr/0004-expert-allowlist.md). Валидатор
(`validateExpert`):

- принимает только директивы из `expertDirectives`; токен — `[a-z0-9_]+`;
- запрещает параметры из файлов (`"/…"`, `parameters(…)`) во всех директивах;
- `deny_info` — только `ERR_*`, `http(s)://` URL (с кодом 30x) или `TCP_RESET`;
- `cache_peer` — IP-литерал без zone вне защищённых сетей; частный — только при
  `allow_private_destinations`; опции-пути запрещены;
- имена `sc_` допустимы только как `sc_http_listener` и `sc_tls_listener` в
  `http_access`;
- секция не длиннее 128 KiB.

Ошибка `squid -k parse` возвращается номером строки секции или итогового конфига,
без текста Squid. Шаблон секции (`/configuration/expert-template`) без клиентов —
рабочий `http_access deny all`.

## Отключение клиента

Reload меняет правила для новых запросов; открытый `CONNECT` живёт до закрытия.
Принудительного разрыва туннелей нет, UI об этом предупреждает.

## Обход прокси

Настройка прокси — добровольный маршрут приложения. Если клиент обязан ходить
через прокси, firewall на границе сети разрешает ему только listener прокси, DNS и
нужные инфраструктурные сервисы и закрывает прямой IPv4/IPv6 и UDP/443. Разрешённый
сайт сам может предоставлять туннель; список доменов — не DLP.
