# Вводные, предложения и вопросы

## Подтверждено владельцем 27.10.2026

- Используется контейнерный образ `ubuntu/squid` на одной выделенной VM.
- Управление — web, доступ к нему защищён паролем.
- Клиентские VM ходят через прокси в интернет, включая APT/deb.
- Одним VM нужен весь HTTP/HTTPS, другим — только определённые ресурсы.
- Первая ценность — управление доступом и диагностика.
- HTTPS сайтов — только сквозной CONNECT; серверный TLS к прокси сохраняется.
- Один собственный image на базе `ubuntu/squid`, один контейнер: отдельный Squid
  и Go-бинарник со встроенным UI, API и модулем применения, под Pebble.
- Host runner, systemd unit приложения и отдельный edge container не нужны.
- Весь исходный код приложения и тестов размещается в src/.
- Визуальные акценты панели предлагаются исполнителем.
- Количественные сведения о VM/пользователях не сохраняются в документах.

## Рекомендовано, но ещё не утверждено

Go API/HTTPS, React/TypeScript UI, SQLite и single-service Compose уже реализованы
по поручениям о разработке. Их проверенный статус — в capability report.
Дополнительные учётные записи и роли теперь подтверждены владельцем; состав ролей ещё не выбран.
Панель через HTTPS на management-сети. Сейчас реализован администратор;
несколько учётных записей и роли входят в дальнейшую разработку.
IP VM — базовая идентичность клиента. Default deny и защита private destinations.
TLS к прокси — целевой транспорт, совместимость проверяется до включения.

Статусы решений перечислены в [реестре ADR](../adr/README.md); наличие Proposed
документа не является согласованием. Текущий объём оставшихся работ определяет
[roadmap](../plans/roadmap.md), а не все первоначальные предложения сразу.

## Что нужно выяснить до установки

| Вопрос | Почему влияет | Предложение до ответа |
| --- | --- | --- |
| ОС/архитектура proxy VM и клиентских VM? | Образ, Docker и TLS/APT совместимость | Ubuntu LTS на proxy VM; версии уточнить |
| Статические IP, DHCP или NAT между VM? | Squid должен видеть отдельный src IP | Статические адреса/резервации; проверить capture/log |
| Нужен запрет прямого egress? | Proxy env не предотвращает обход | Если нужен, запрет на сетевом уровне, включая IPv6/UDP |
| Где management-сеть и кто имеет доступ? | Привязка 443 и firewall | VPN/private management, без публичного входа |
| DNS-имя панели и прокси, кто выдаёт TLS? | SAN, доверие, ротация | Действующая инфраструктурная PKI или собственный серверный CA |
| Есть внутренние репозитории/private ресурсы? | Защита RFC1918 запретит и полезные адреса | Уже есть allow_private_destinations; точные исключения только при потребности |
| Что именно значит «ресурс»? | Доступная видимость HTTPS ограничена | Домен и порт; URL-путь HTTPS недоступен |
| Какие роли и права нужны в панели? | Несколько users и роли уже подтверждены | Матрицу read/edit/apply/users/logs согласовать до реализации |
| Нужны мгновенные отключения активных туннелей? | Reload не разрывает их гарантированно | Новые соединения запрещаются, старые живут до закрытия/таймаута |
| Как долго хранить логи и куда делать backup? | Диск, чувствительные данные | Предварительные сроки в observability, уточнить |
| Требуется работа при отказе VM? | Один узел не даёт HA | Документированный restore, без обещания HA |

Не блокирует проектирование: бренд, домен, точный UI framework, продуктовая лицензия.
До публикации владелец выбирает лицензию и канал сообщений об уязвимостях.

## Уточнения владельца: клиенты и конфигурация

VM — только пример; интерфейс управляет произвольными клиентами, сетями и группами.
Нужны визуальные настройки и экспертный squid.conf (ADR 0007 Accepted).
Пароль администратора хранится только как salted one-way hash, исходное значение
не сохраняется. CLI reset должен менять verifier и отзывать sessions.
Ограничение исходного узкого UI не является границей конечного продукта.

## Уточнение объёма после анализа остатка

Владелец попросил пересмотреть задачи с учётом простой SQLite/volume архитектуры.
Не строить крупную подсистему там, где достаточно короткой процедуры оператора.
Первоначальные необязательные идеи не становятся требованиями от упоминания
в specs. Более позднее уточнение владельца включает users/roles и proxy auth;
остальные дополнительные функции и архитектурные расширения исключены.
Проверки границ доступа и уже реализованные гарантии безопасности сохраняются.

## Прямое уточнение владельца: users/roles и proxy identity

Подтверждено: дополнительные пользователи и роли панели; proxy authentication
по логину и паролю. Это scope, не подтверждение выбранного протокола,
role matrix или готовности Squid image. После объяснения владелец исключил mTLS:
клиентские сертификаты для аутентификации не нужны. SSO/IdP и собственный CA
не требуются. Серверный TLS к proxy сохраняется, TLS сайтов сквозной.

Остальные предложенные расширения исключены, включая HA/Kubernetes,
runner/очереди/сервисы, замену SQLite, полную реляционную переделку,
zero-downtime upgrades и новые агентские документы ради структуры.
Точный текущий объём и порядок — [roadmap](../plans/roadmap.md).
