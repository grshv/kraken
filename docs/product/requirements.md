# Требования

Статус: подтверждённый сценарий и предложенные критерии первой версии.
Дата: 2026-10-27. Имена и IP во всех примерах синтетические.

## Задача

На выделенной VM запускается один собственный контейнер на базе `ubuntu/squid`,
с Go-приложением и отдельным Squid под Pebble. Другие VM используют его
как явный forward proxy для HTTP/HTTPS, в том числе APT и загрузки deb-пакетов.
Администратор управляет доступом через web-интерфейс с паролем и видит причины
отказов. Для одной VM разрешён весь web, для другой — выбранные ресурсы.

В архитектуре должны быть предусмотрены TLS между клиентом и прокси, а также
SSL Bump с доверенным CA на VM. Конкретный режим включается явно.
Кеширование вторично относительно доступа и диагностики.

## Пользователи и сценарии

- Администратор входит, проверяет состояние прокси, добавляет VM по IP/CIDR,
  назначает режим и видит точное влияние изменений перед применением.
- Администратор задаёт список доменов для VM с ограниченным доступом.
  UI различает точный домен и домен с поддоменами.
- Администратор включает/выключает VM, сравнивает ревизии, применяет и откатывает.
- Оператор ищет отказ по времени, адресу VM и назначению; получает HTTP/Squid-код,
  наблюдаемую причину и сведения о полноте данных.
- Администратор получает инструкции APT/curl для выбранного TLS-профиля.
- При необходимости администратор подключает проверенный профиль SSL Bump,
  понимая требования к CA, приложениям с pinning и исключениям inspection.

## Первая поставка: доступ и диагностика

1. Одна управляемая инсталляция Squid и локальная панель; несколько записей VM.
2. Серверная сессия, локальный bootstrap администратора, HTTPS-панель.
3. Персональные политики `all_web` и `allowlist`; IPv4/IPv6 учитываются явно.
4. Draft → preview → validate → apply → verify → rollback, история действий.
5. Реальное состояние runtime отдельно от состояния API и внутреннего runtime module.
6. Ограниченный просмотр access logs, фильтры, разбор отказов и инструкции клиентам.
7. Резервная копия настроек и проверяемое восстановление.
8. Контракт TLS-профилей; TLS к прокси включается после image/client spike.
   SSL Bump реализуется отдельным этапом с собственными acceptance tests.
   Если inspection нужен в первом релизе, этап переносится до его приёмки.

## Границы

- Не маршрутизатор для произвольных TCP/UDP: SSH, QUIC и DNS сами по себе через
  HTTP forward proxy не пойдут. HTTP/3 не становится поддержанным автоматически.
- Нет автоматической установки настроек на чужие VM в MVP: выдаём инструкции.
- Нет редактирования произвольных директив Squid из браузера.
- Нет кластера, HA, Kubernetes, биллинга, VPN, SOCKS и управления другими Docker
  контейнерами. Для одного узла это не требуется подтверждённым сценарием.
- Не обещается точная идентификация человека по IP VM.
- Доменный allowlist не доказывает тип содержимого HTTPS и не исключает туннель
  к сервису на разрешённом адресе. Для строгого контроля нужны дополнительные меры.
- Общий кеш пакетов, лимиты bandwidth, OIDC и роли операторов — следующие решения.

## Критерии приёмки

| ID | Условие | Ожидаемый результат |
| --- | --- | --- |
| AC-01 | Запрос от незарегистрированной VM | Отказ, без исходящего запроса к цели |
| AC-02 | VM в `all_web`, разрешённый внешний HTTP/HTTPS | Работает, защитные запреты сохраняются |
| AC-03 | VM в `allowlist`, разрешённый/чужой домен | Первый доступен, второй запрещён |
| AC-04 | Невалидная политика или squid.conf | Действующая ревизия и трафик не меняются |
| AC-05 | Reload/проверка после apply неуспешны | Проверяемый rollback либо явное degraded |
| AC-06 | Два администратора редактируют одновременно | Устаревшая версия получает conflict |
| AC-07 | Процесс Go-панели упал | Pebble перезапускает его отдельно; Squid продолжает работу с последними правилами |
| AC-08 | Клиент обращается к metadata/localhost/private destination | Отказ во всех режимах VM |
| AC-09 | Вход/изменение без валидной сессии или CSRF | Отказ на сервере, событие аудита |
| AC-10 | Просмотр HTTPS в туннеле | Показаны host:port и ограничения наблюдаемости |
| AC-11 | TLS к прокси, неверный сертификат | Клиент отвергает его; инструкция не отключает проверку |
| AC-12 | SSL Bump для выбранной VM | Клиент доверяет управляемому CA; исключения splice проверены |
| AC-13 | Восстановление из копии | Сверены ревизия, hash, секреты и реальный запрос клиента |
| AC-14 | Выключение VM | Новые запросы запрещены; судьба открытых туннелей объяснена |

## Нефункциональные цели

Целевые значения для проверки, не результаты нагрузочного теста: открытие обычной
страницы панели до 2 секунд в локальной сети; ограниченный timeout apply;
сохранение трафика при отказе панели. Нагрузку и размеры диска определяем
измерениями, без фиксации сообщённых владельцем количественных вводных.

Остановка/обновление общего контейнера прерывает оба сервиса и активные туннели.
При полном отказе VM доступ через неё прекращается. Одна VM — единая точка отказа.
Желаемые RPO/RTO и необходимость резервного узла остаются открытыми.
