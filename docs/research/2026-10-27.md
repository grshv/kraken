Проверены открытые первичные источники в интернете 27.10.2026.

## Squid и контейнер

- [Canonical ubuntu/squid](https://hub.docker.com/r/ubuntu/squid): источник образа,
  описание каналов, путей и эксплуатации. Страница показывает Pebble entrypoint;
  на дату исследования среди каналов есть beta/edge, а команды примеров могут
  использовать старые теги. Не выбирать image по одному примеру и не использовать
  `latest` как production pin. Конкретный digest пока **не выбран**.
- [Pebble](https://ubuntu.com/docs/pebble/): отдельный service manager. Значит,
  управление процессом Squid нужно проверить, а не подменять сигналом PID 1.
- [Squid http_access](https://www.squid-cache.org/Doc/config/http_access/) и
  [security pitfalls](https://wiki.squid-cache.org/SquidFaq/SecurityPitfalls):
  явный deny-all, доверенные источники, manager и safe ports составляют основу ACL.
- [Squid HTTPS](https://wiki.squid-cache.org/Features/HTTPS): туннель CONNECT
  ограничивает видимость; host:port не равен расшифрованному HTTP-запросу.
- [https_port](https://www.squid-cache.org/Doc/config/https_port/): TLS listener
  зависит от compile options GnuTLS/OpenSSL и серверного сертификата.
  Нельзя переносить конфигурацию между major versions без проверки availability.
- [Squid CLI, Ubuntu manpage](https://manpages.ubuntu.com/manpages/resolute/man8/squid.8.html):
  parse и reconfigure — отдельные control operations.
- [Обсуждение разработчиков Squid о validate](https://ml-archives.squid-cache.org/squid-dev/2024-September/009918.html):
  синтаксическая проверка не доказывает смысловую корректность политики.

Наши решения: renderer с typed policy, image capability gate, directory mount,
LKG и durable journal. Это проектные выводы, а не обещания официального image.

## Сеть, клиенты и безопасность

- [Docker daemon security](https://docs.docker.com/engine/security/) и
  [Docker socket](https://docs.docker.com/engine/security/protect-access/):
  доступ к daemon имеет высокие полномочия. Поэтому web не получает Docker socket.
- [Docker firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/):
  published ports и ufw взаимодействуют не так, как обычный host listener.
  Фильтрацию проверяем на фактическом backend и с внешней машины.
- [APT HTTP](https://manpages.debian.org/bookworm/apt/apt-transport-http.1.en.html),
  [APT HTTPS](https://manpages.debian.org/trixie/apt/apt-transport-https.1.en.html):
  proxy задаётся в Acquire scopes; HTTPS transport поддерживает общие опции HTTP.
  Клиентские настройки сверяются с установленной версией APT.
- [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
  [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
  [CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html):
  пароль и сессия проектируются серверно, cookie и CSRF отдельно от UI.

Первоначальное предложение отдельного host runner заменено решением владельца:
один контейнер, Go со static UI и Squid под Pebble, без Docker socket.
См. [ADR 0006](../adr/0006-single-container.md). Внутренний runtime module не даёт
изоляции от web-кода. Сетевой запрет direct egress — отдельная наша рекомендация.
Эти решения не являются требованиями формата AGENTS.md.

## Предложенный стек

- [Go documentation](https://go.dev/doc/) и [embed](https://pkg.go.dev/embed):
  один компилируемый executable управления со встроенным статическим UI.
- [React: build from scratch](https://react.dev/learn/build-a-react-app-from-scratch)
  описывает Vite и компромиссы такого пути; выбор SPA оправдан закрытой панелью
  с отдельным Go backend, без SSR/SEO. Это не утверждение о предпочтении SPA везде.
- [Vite guide](https://vite.dev/guide/): официальный путь React/TypeScript build.
  Точные runtime/tool versions и lockfile выбираются при первом кодовом срезе.
- [SQLite WAL](https://www.sqlite.org/wal.html) и
  [backup](https://www.sqlite.org/backup.html): local disk и согласованный backup.
