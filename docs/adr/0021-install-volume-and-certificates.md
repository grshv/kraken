# ADR 0021: подготовка тома и собственный CA установки

Дата: 2026-11-02. Статус: Accepted по решениям владельца 02.11.2026
([decisions](../product/decisions.md), «Продукт и развёртывание»).

Дополняет набор capabilities из [ADR 0019](0019-alpine-upstream-squid.md)
(`CHOWN` вдобавок к `SETUID`, `SETGID`, `KILL`); остальное в ADR 0019 действует.

## Контекст

Установка по README не работала без ручных шагов. Каталог хоста вместо тома
(`./data:/var/lib/kraken`) перекрывал раскладку образа, а root в контейнере без
capabilities не мог передать его UID 10013/13: панель падала на правах. Без
сертификатов панель уходила в цикл перезапусков до ручной команды. Dev-сертификат
был самоподписанным leaf только для `localhost`: импортировать его как CA нельзя,
по IP или имени сервера проверка не проходила, а HSTS с `includeSubDomains;
preload` не давал открыть панель после предупреждения браузера. Свой сертификат
прокси требовал отдельного override с двумя переменными путей.

## Решение

- PID 1 — `kraken entrypoint` от root, затем `exec` Pebble. Если корень тома уже
  `10013:13 0750`, ничего не меняется. Иначе entrypoint с `CAP_CHOWN` создаёт и
  передаёт владельцам `data/`, `certs/`, `log/` (`backups/`, если есть) по раскладке
  ADR 0015. Каталог с другими именами, symlink, hard link или специальными файлами
  отклоняется без изменений. `DAC_OVERRIDE` и `FOWNER` не добавляются: root
  временно становится владельцем каталога, чтобы пройти его. Сервисы Pebble
  запускаются под `proxy`/`kraken` без эффективных capabilities.
- `serve` при старте без серверных сертификатов выпускает собственный CA установки
  (ECDSA P-256, 10 лет, `pathlen 0`, критичные name constraints только на имена
  установки) и подписанные им сертификаты панели и TLS-прокси (397 дней,
  `serverAuth`). Имена: `localhost`, host из `KRAKEN_PUBLIC_ORIGIN`, адреса
  публикации `KRAKEN_MANAGEMENT_BIND`/`KRAKEN_PROXY_BIND` и `KRAKEN_CERT_NAMES`.
  Ключ CA лежит в `certs/` (0600, UID 10013) и из-за constraints может подписать
  только те имена, которыми панель уже владеет. Неполный набор файлов — ошибка, а не
  перезапись.
- Свой сертификат ставит `kraken cert install panel|proxy`: сертификат и ключ одним
  PEM через stdin, проверка пары, срока, `serverAuth` и SAN; права выставляет сама
  команда. Override с путями к файлам удалён.
- TLS-listener прокси включён по умолчанию; 3129 публикуется вместе с 3128.
  Существующая установка получает его при старте автоматическим service-update
  (тот же журналируемый pipeline с откатом, черновик не читается).
- HSTS — `max-age=31536000` без `includeSubDomains` и `preload`.
- Сеть остаётся bridge: host network не используется. Несколько адресов хоста —
  дополнительные записи `ports` в `compose.override.yaml`.

## Последствия

- Root PID 1 может сменить владельца файлов внутри тома, но только на время
  подготовки и только в каталоге с раскладкой Kraken.
- Доверие к панели и прокси — один импорт `ca.crt` (`kraken cert ca`). Смена имён
  вне constraints создаёт новый CA (`kraken cert renew`), его нужно импортировать заново.

## Альтернативы

- Только сообщение с командой `chown` на хосте: capabilities не меняются, но
  быстрый старт снова требует ручного шага.
- Ждать сертификаты без падения: цикл исчезает, но панель недоступна до команды.
- CA без ключа на томе: компрометация тома не даёт подписи, но любое продление
  требует нового импорта; name constraints делают хранение ключа безопасным.
- Host network со списками адресов внутри контейнера: настоящий source IP и любые
  адреса без override, но контейнер теряет сетевую изоляцию, а диагностические
  listeners Squid оказываются на loopback хоста. Отклонено владельцем.
