# ADR 0017: хранилище телеметрии

Дата: 2026-10-29. Статус: Accepted по решению владельца 29.10.2026
([decisions](../product/decisions.md), пункт «Хранение»).

Заменяет [ADR 0011](0011-durable-diagnostics.md).

## Контекст

История запросов хранилась в управляющей БД JSON-строками: до 50 000 событий и
30 дней. Статистика пересчитывалась по сырым событиям на каждый запрос, на одном
соединении с входом и применением. Владелец требует историю и статистику на 1–3 года
без внешней БД; содержимое запросов не записывается. Замер на синтетике: JSON-схема —
около 850 байт на событие, колонки со словарём доменов — около 90.

## Решение

- Телеметрия отделена от управляющей БД: каталог `app/telemetry/` с файлами
  `events-YYYY-MM.db` (сырые события месяца, колонки, словарь доменов) и `rollups.db`
  (агрегаты). Управляющая БД (`control.sqlite3`) хранит пользователей, ревизии,
  операции и аудит.
- Сбор: access.log и ротации читаются порциями по checkpoint (inode, device, offset);
  события и checkpoint пишутся одной транзакцией в файл текущего месяца. Сырой текст
  и URL path/query/userinfo не сохраняются. Клиент определяется по уникальному
  совпадению активной политики при сборе и позднее не переписывается.
- Свёртка: после записи события с id выше отметки месяца агрегируются в `rollups.db`
  одной транзакцией вместе с новой отметкой; повтор идемпотентен. Потерянный
  `rollups.db` пересобирается из хранимых месячных файлов.
- Сроки: сырые события — по возрасту (по умолчанию 90 дней) и бюджету диска (по
  умолчанию 5 GiB), удалением целых месячных файлов, текущий месяц не удаляется;
  15-минутные и суточные агрегаты — 3 года, почасовые — 30 дней.
- Статистика и инспектор читают агрегаты; объяснение события и влияние черновика —
  сырые события за 24 часа. Журнал листается по cursor, привязанному к фильтрам и
  области; удалённые ретеншном события отмечаются как gap.
- На каждый файл — одно соединение записи и пул чтения: чтения не ждут запись.
- Повреждённый файл телеметрии откладывается как `.broken-<unix>` и создаётся
  заново; панель продолжает работать.

## Альтернативы

- Одна БД с DELETE по ретеншну: удаление миллионов строк, VACUUM и рост бэкапа.
- Внешняя БД или log cluster: исключены владельцем для одного узла.
- Сжатые JSONL-архивы: меньше по размеру, но без индексов и поиска.

## Последствия

- Бэкап обязателен для `control.sqlite3`, рекомендован для `rollups.db`; месячные
  файлы — по желанию.
- Агрегаты переживают удаление сырых событий: статистика за год доступна, поиск
  отдельных событий — в пределах хранимых месяцев.
- Локальная телеметрия не forensic archive: доступ к volume позволяет её изменить.
- Пулы и таймауты управляющей БД и пороги диска — отдельное решение.
