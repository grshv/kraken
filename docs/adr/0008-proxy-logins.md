# ADR 0008: логины прокси

Статус: Accepted. Дата: 2026-10-27.

## Контекст

Не все клиенты различимы по адресу: за NAT несколько устройств делят один IP.
Нужна идентификация по логину и паролю без клиентских сертификатов и внешних
IdP, и смена пароля должна действовать сразу, несмотря на кеш Squid.

## Решение

- Логин прокси — отдельная учётная запись (`proxy_accounts`), не доступ в панель.
  В БД только Argon2id PHC; пароль не попадает в снимок, конфиг, argv, env, логи и
  ответы API.
- Клиент с логином связывает адреса источника и логин; доступ по-прежнему определяет
  режим и список клиента. Успешный вход сам по себе доступа не даёт.
- Basic-пароль принимается только на TLS-listener 3129.
- Squid вызывает единственный helper — тот же исполняемый файл с фиксированными
  argv: `kraken proxy-auth` проверяет пароль, `kraken proxy-auth --state` без кеша
  на каждом разрешаемом запросе сверяет generation (SHA-256 от verifier) и
  включённость. Helper читает экспорт верификаторов в tmpfs, а не SQLite
  ([ADR 0009](0009-separate-squid-uid.md)).
- Basic TTL — 1 секунда (ноль в Squid зацикливает проверку); generation ACL делает
  смену пароля и блокировку немедленными.
- Разные логины могут делить адреса за NAT; пересечение клиента без логина с
  клиентом с логином или одинаковых логинов запрещено.

## Альтернативы

- Клиентские сертификаты (mTLS): нужна выдача и отзыв сертификатов, исключено
  владельцем.
- Произвольный `auth_param` в expert-секции: открывает запуск процессов.

## Последствия

- Squid видит Argon2id-верификаторы включённых логинов — необходимый минимум.
- Начатый запрос и открытый `CONNECT` после блокировки логина могут завершиться.
- Клиенты с логином не совмещаются с expert-режимом.
