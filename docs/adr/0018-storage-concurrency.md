# ADR 0018: параллельный доступ к управляющей БД

Дата: 2026-10-29. Статус: Accepted по решениям владельца 29.10.2026
([decisions](../product/decisions.md), пункты «Хранение» и «Поставка и обслуживание»).

Заменяет [ADR 0009](0009-single-process-concurrency.md).

## Контекст

ADR 0009 сериализовал все обращения к SQLite одним соединением и запрещал второй
процесс с той же БД. Это давало корректность, но любое долгое чтение задерживало
вход и применение, а каждый авторизованный запрос писал отметку сессии. Оператор
теперь обслуживает экземпляр командой `kraken` внутри контейнера, то есть вторым
процессом рядом с `serve`. Телеметрия вынесена в отдельные файлы
([ADR 0017](0017-telemetry-storage.md)).

## Решение

- Один процесс `serve` владеет черновиком, ревизиями, операциями, runtime worker и
  сбором событий. In-process mutex черновика и операций и `flock` runtime остаются.
- Управляющая БД открывается двумя пулами: writer — одно соединение, транзакции
  `BEGIN IMMEDIATE`, `busy_timeout`; reader — несколько соединений `query_only`.
  WAL позволяет читателям не ждать запись.
- Отметка активности сессии пишется не чаще раза в минуту; обычный запрос — чтение.
- Запросы к БД из API идут с дедлайном; истёкший дедлайн и занятая БД дают
  `503 storage_busy`, а не зависание.
- CLI оператора — допустимый второй процесс. Он меняет только пользователей,
  сессии и пароли короткими транзакциями под блокировкой SQLite и делает
  онлайн-копию через `VACUUM INTO`. Черновик, ревизии, операции и runtime state CLI
  не меняет (кроме `service-update`, который идёт тем же путём, что и API, под `flock`).
- Нехватка места проверяется до изменения: изменения отвечают `507 storage_full`,
  сбор событий приостанавливается раньше.

## Альтернативы

- Одно соединение (ADR 0009): простота ценой блокировок чтением.
- Внешняя БД: исключена владельцем.
- CLI через HTTP API панели: требует работающей панели и учётных данных, а сброс
  пароля нужен именно когда войти нельзя.

## Последствия

- Второй экземпляр `serve` на той же БД по-прежнему не поддерживается; HA нет.
- Блокировки последнего администратора и отзыв сессий проверяются в транзакции
  записи одинаково для API и CLI.
- Негативные тесты: конкурентные чтения во время записи, гонка сброса пароля и
  отметки сессии, 507 до записи, 503 при истёкшем дедлайне.
