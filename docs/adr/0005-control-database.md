# ADR 0005: управляющая БД

Статус: Accepted. Дата: 2026-10-29.

## Контекст

Управляющие данные — пользователи, сессии, черновик, ревизии, операции, журнал
применения и аудит. Их немного, но вход и применение не должны ждать тяжёлых чтений,
а оператор обслуживает экземпляр CLI вторым процессом рядом с `serve`.

## Решение

- Одна SQLite `data/control.sqlite3` в WAL. Снимки конфигурации — JSON в таблице `kv`
  (`draft`, `revision:<id>`, `runtime.journal`, `runtime.last_good`); пользователи,
  сессии, логины прокси, область менеджера, операции, аудит и отметки
  уведомлений — отдельные таблицы. Ссылочную целостность снимка проверяет
  `policy.Validate`, версию черновика — optimistic lock.
- Два пула: запись — одно соединение с `BEGIN IMMEDIATE`; чтение — несколько
  соединений `query_only`. Читатели не ждут писателя.
- Каждый вызов хранилища получает контекст и сам ограничен 3 с (`store.OpTimeout`).
  Истёкший дедлайн или занятая БД — `503 storage_busy`, а не зависание.
- Отметка активности сессии пишется не чаще раза в минуту и не дольше 250 мс;
  обычный запрос только читает.
- Свободное место проверяется до записи: меньше 64 MiB — изменения отвечают
  `507 storage_full`; меньше 512 MiB — останавливается сбор событий.
- Миграции вперёд, DDL и данные в одной транзакции, checksum фиксируется. БД с
  чужим checksum не открывается.
- CLI меняет только пользователей, сессии и пароли короткими транзакциями и делает
  онлайн-копию через `VACUUM INTO`. Черновик и ревизии меняет только `serve`;
  исключение — `service-update`, который идёт тем же путём применения под `flock`.

## Альтернативы

- Полная реляционная схема клиентов и политик: больше миграций без выгоды при
  объёмах одного узла.
- Одно соединение на всё: проще, но любое долгое чтение задерживает вход.
- CLI через HTTP API: требует работающей панели и учётных данных, а сброс пароля
  нужен именно когда войти нельзя.

## Последствия

- Проверка последнего администратора и отзыв сессий выполняются в транзакции записи
  одинаково для API и CLI.
- Телеметрия хранится отдельно и не может заполнить управляющую БД
  ([ADR 0011](0011-telemetry-storage.md)).
- Ревизии старше последних 20, на которые не ссылается успешная операция, удаляются;
  аудит хранится 3 года.
