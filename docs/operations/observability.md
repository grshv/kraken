# Наблюдаемость и диагностика

## Источники

| Источник | Что содержит |
| --- | --- |
| access.log Squid (`log/`) | Запросы клиентов в формате `kraken`: родной `squid` и причина отказа `%{sc_deny}note` |
| Логи Pebble (`pebble logs`) | Старт, reload, ошибки Squid, панели и helper |
| Журнал применения | Этап, хеши кандидата и LKG, исход ([configuration-lifecycle](../architecture/configuration-lifecycle.md)) |
| Логи панели | Структурированные: ID запроса и операции, автор, статус, длительность |
| Аудит | Кто изменил клиента, политику, пользователя, логин прокси, кто применил ревизию |

Вывод Squid, URL и учётные данные не попадают в API и логи панели. Все поля в UI
выводятся текстом, без HTML.

## Сбор журнала запросов

- Фоновый сборщик читает access.log и ротации `.0`…`.29` от старых к новым порциями
  до 256 KiB. Пока есть хвост, следующая порция читается сразу; догнав лог, сборщик
  ждёт 2 секунды. Остановка панели прерывает цикл после текущей порции.
- Позиция чтения — inode, device, offset, хеш последних 64 байт и generation; до 64
  файлов отслеживаются, чтобы продолжить без повторов. События и позиция пишутся
  одной транзакцией месячного файла телеметрии; дубликаты по `source_id`
  игнорируются.
- Строка до 16 KiB разбирается до сохранения; незавершённая строка ждёт конца;
  слишком длинная пропускается. Битые записи, обрезанная ротация и исчезнувший
  файл отмечают постоянный разрыв (`gap`). Полнота до первого запуска сборщика
  неизвестна.
- Клиент определяется уникальным совпадением source IP и, для клиентов с логином,
  логина в действующей ревизии на момент сбора. Неоднозначное совпадение — без
  клиента. Позднее изменение клиента запись не переписывает.
- Одинаковые события секунды схлопываются в одну запись со счётчиком `count`
  ([data-model](../architecture/data-model.md#телеметрия)).
- Запросы с loopback (canary, manager) в access log не пишутся.

## API журнала

Все ручки — только чтение, с областью менеджера ([ADR 0007](../adr/0007-admin-and-manager-roles.md)).

| Ручка | Что отдаёт |
| --- | --- |
| `GET /events` | Запросы по курсору от новых к старым; новые записи не сдвигают открытые страницы |
| `GET /events/facets` | Счётчики результата, клиентов, методов и гистограмма за окно |
| `GET /events/domains` | Запросы по доменам (до 500) с источниками (до 20) и итогами для сводки |
| `GET /events/clients` | Известные клиенты журнала для фильтра (до 200) |
| `GET /activity` | Сводка за 15 мин–30 дней: частые источники и проблемы (до 10 групп) |
| `GET /statistics` | Суточная статистика по часовым корзинам |
| `GET /audit` | Аудит по курсору; фильтры автора, действия и `entity_id` |

Фильтры `/events`: `client_id`, `method`, `deny_reason` (повторяемые, «любой из»),
`unmatched` (неописанные источники), `failures_only` или `allowed_only`,
`source_ip`, `destination` (подстрока), `from`/`to` (RFC 3339, полуоткрытый интервал).
Фасеты и домены требуют окно не длиннее 31 суток; окно длиннее суток на целых часах
считается по часовому агрегату `journal_1h`. Шаг гистограммы — `1m`, `15m` или `1h`,
не больше 1440 корзин. Дедлайн — 5 с. Ошибка параметров — `400 invalid_filter`.

Отказ — `DENIED` или `FAIL` Squid либо статус прокси ≥ 400. HTTP 403 от сайта —
не отказ прокси. Курсор — позиция, а не credential: он привязан к фильтрам и
области, поэтому произвольный курсор не расширяет доступ.

## Объяснение отказа

`GET /inspector/events/{id}/explain` объясняет отказ по текущим правилам: защита,
«запрещено для всех», неописанный источник, выключенный клиент, логин, режим
«нет доступа», домена нет в итоговом списке. Если сейчас запрос был бы разрешён —
это исторический отказ. Точное правило, которого нет в логе, не угадывается.
`GET /inspector/draft-impact` показывает, каким разрешённым за 24 часа запросам
черновик начнёт отказывать и сколько отказов исчезнет.

## Состояние экземпляра

`GET /api/v1/status` показывает раздельно: панель, процесс Squid, действующую
ревизию, наличие неприменённых изменений, сбор журнала и место на диске.

- `instance`: имя (`KRAKEN_INSTANCE_NAME` или hostname), свободное и полное место
  тома данных (`null`, если `statfs` не удался), время последнего события,
  позиции чтения и применения, `telemetry_bytes`, `events_oldest_at`,
  `telemetry_broken_files`.
- `ingestion`: `state` (`ok`, `storage_low`, `error`) и `observed_at`. Журнал
  считается отстающим, если чтение не удавалось 15 секунд.

Свежесть журнала берётся из сохранённых данных: отсутствие событий не доказывает
отсутствие трафика. Невозможность наблюдения — «неизвестно», а не «не работает».

## Метрики Squid

`GET /squid/metrics` — агрегаты отчётов manager Squid
([ADR 0010](../adr/0010-squid-manager.md)): версия и аптайм, CPU, память, число
активных запросов без служебных, запросы и байты Squid ↔ сайты (`server.all`),
скорости за 5 минут, доля попаданий в кеш. Счётчики байт в отчётах — KiB, API
переводит их в байты. Недоступное значение — `null`; скорости — `null`, пока окно
пустое. Если действующий конфиг собран старым компилятором без manager-listener,
ответ — `configuration_update_required`.

Внешнего экспорта метрик и уведомлений нет: предупреждения видны только в панели.

## Хранение и место на диске

- Сроки хранения событий, агрегатов и аудита — [data-model](../architecture/data-model.md#сроки-хранения).
  Обрезанная сроком история отмечается в конце доступных страниц.
- access.log ротируется больше 10 MiB, но только когда сборщик его дочитал; от
  256 MiB — в любом случае, непрочитанный хвост учитывается как разрыв. Число
  ротаций задаёт настройка Squid (до 30).
- Свободно меньше 512 MiB — сбор событий останавливается
  (`ingestion.state=storage_low`, лог раз в минуту) и продолжается с прежней позиции.
- Свободно меньше 64 MiB — изменения (черновик, ревизии, операции, пользователи,
  логины прокси, область) отвечают `507 storage_full` до записи; чтение, вход и
  выход работают.
- Каждое обращение к управляющей БД ограничено 3 с; таймаут или блокировка —
  `503 storage_busy` с `Retry-After: 2`. Ошибка `statfs` работу не блокирует.
- Аудит в локальной SQLite — не неизменяемое forensic-хранилище.
