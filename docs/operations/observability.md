# Наблюдаемость и диагностика

## Четыре независимых состояния

Панель показывает web health, состояние runtime module, процесс Squid и доступность
проверяемых внешних ресурсов раздельно. «Контейнер запущен» не значит «APT работает».
Каждый статус имеет `observed_at`, источник и stale marker.

## Источники

- Squid access log в формате `kraken` (родной `squid` и причина отказа `%{sc_deny}note`,
  [policies-and-tls](../architecture/policies-and-tls.md)); его поля проверяются integration-тестами на образе.
  Строки старого формата без причины разбираются по-прежнему.
- Squid/Pebble service logs — reload, DNS, startup и TLS/helper failures.
- Внутренний operation journal — этап, duration, candidate/LKG hashes, findings.
- Web structured logs — request/operation ID, safe actor ID, status, duration.
- Audit — кто изменил клиента, политику, сертификатную ссылку и кто применил ревизию.

Потоки разные по retention и чувствительности; один бесконечный log stream не нужен.

## Access log pipeline

Фоновый reader читает порциями до 256 KiB из фиксированных access.log и ротаций
.0… .29, в порядке от старых к новым. Пока в логе есть непрочитанный хвост, следующая
порция читается сразу; догнав лог, reader ждёт 2 секунды. Остановка панели прерывает
цикл после текущей порции. Одинаковые события порции в пределах секунды схлопываются
в одну запись со счётчиком `count` ([data-model](../architecture/data-model.md#диагностическая-история)):
поток повторов не раздувает журнал и диск, а счётчики остаются точными. Checkpoint содержит
inode/device, offset, hash последних 64 bytes и generation. До 64 identities
(включая временно исчезнувшие файлы) сохраняются для продолжения без replay. События и checkpoint
сохраняются одной транзакцией месячного SQLite-файла телеметрии, строка получает
id вида `<YYYYMM>-<rowid>`; дубликаты по исходному `source_id` игнорируются.
После рестарта чтение продолжается без повторной вставки. Rename rotation
сохраняет позицию; уменьшение размера или несовпадение anchor отмечает truncation.
Одинаковое содержимое при подмене inode/mtime не обещает обнаружения всех потерь.

Строка до 16 KiB разбирается до сохранения. Незавершённая строка текущего файла
ждёт окончания; oversized строка пропускается до newline. Некорректные записи,
оборванный конец ротации и исчезновение отслеживаемого файла помечают sticky gap.
Первое чтение начинается с доступных ротаций: до установки сборщика полнота
неизвестна. Наличие следующей страницы обозначает next_cursor отдельно от gap.

Сохраняются source IP, destination host:port, method, Squid result, proxy status,
duration и bytes. URL path/query/userinfo не попадают в нормализованную историю.
Сырой файл Squid может содержать URL и остаётся чувствительным: это отдельный
источник с файловыми правами/rotation. Для HTTPS доступны только CONNECT metadata;
длительные туннели логируются при закрытии. Исторические ACL/revision неизвестны.

Имя/ID клиента — уникальное совпадение source IP/CIDR и, для auth-bound clients,
logged proxy username в активном manifest при сборе (policy_at_ingest), включая подписи источников в expert mode. Неоднозначные
совпадения остаются unknown. Изменение клиента не переписывает сохранённую запись.
Фильтр включает сохранённые ID, даже если клиента уже нет в текущем draft;
список показывает до 200 последних известных клиентов.

GET /events читает историю из БД и не запускает ingestion. Курсор привязан к
фильтрам и идёт по убывающей последовательности, поэтому новые запросы не сдвигают
уже открытые страницы. Доступны точный client_id и failures_only (DENIED/FAIL либо
proxy HTTP status >= 400). Неизвестный matched ACL не угадывается.
Панель показывает последнее успешное чтение, backlog, source availability,
число пропущенных строк и stale после 15 секунд без успешного чтения.
Ошибка API оставляет показанные записи с предупреждением об устаревании.
Все поля выводятся текстом, без HTML и исполнения ссылок/команд.

GET /audit показывает actor/action/entity/time из audit_events с точными
фильтрами actor/action и cursor. Это журнал принятых действий: итог apply смотрят
в operation/history. Пароли, session tokens, ключи и тела конфигураций туда не
добавляются. Доступ к событиям, /events/clients и аудиту имеют admin и manager; менеджер видит
только свою область ([ADR 0016](../adr/0016-admin-and-manager-roles.md)). Хранилище —
[ADR 0017](../adr/0017-telemetry-storage.md).

## Метрики

Предлагаемые counters/gauges: squid_up, control_up, config_drift,
last_verified_timestamp, operations_total по action/outcome, apply_duration,
requests_total по ограниченному outcome, bytes, active_connections если доступны,
log_ingest_lag, dropped_records, disk_free, cert_not_after.

Не label-ить метрики полными URL, query, operation UUID или произвольными hostnames.
Per-client totals допустимы с ограниченным числом зарегистрированных клиентов.
Назначение/запрос искать в bounded log view, а не в бесконечной cardinality метрик.

Bytes CONNECT могут быть только частью измеряемого трафика в выбранном формате;
до проверки не называть их точной экономией bandwidth или полным двунаправленным
учётом. Для кеша показывать только подтверждённые HTTP hit/miss counters.

## Объяснение отказа

UI показывает наблюдаемый факт (например TCP_DENIED/403), policy revision на момент
запроса если известна, VM и requested destination. Если совпавший ACL не был
записан, точное правило не угадывать. Симулятор политики — отдельная оценка,
подписанная «по текущим правилам», а не историческое доказательство.

Для HTTPS tunnel: CONNECT status, host:port, длительность; содержимое сайта скрыто.

## Retention и алерты

Реализовано: нормализованные события — 90 дней по возрасту и бюджет 5 GiB
(oldest-first, текущий месяц не удаляется) в месячных файлах `events-YYYY-MM.db`;
агрегаты `rollups.db` — часовые 30 дней, 15-минутные и суточные 3 года; audit —
3 года (`store.AuditRetention`), без лимита строк. Обрезание истории обозначается
у конца доступных страниц; sticky gap также хранит известные потери reader. Сырые
файлы удаляются целиком по ретеншну; агрегаты чистятся чанками по 5000 строк.
`PRAGMA wal_checkpoint(PASSIVE)` раз в 10 мин и `PRAGMA optimize` суточно
обслуживают управляющую БД; `journal_size_limit=64MiB` ограничивает WAL sidecar.
Raw logs ограничены rotation count и периодической ротацией по размеру, не
автоматическим TTL. Лог ротируется при размере больше 10 MiB, только когда reader
дочитал его (последний checkpoint без backlog): иначе ротация отложена, чтобы не
потерять непрочитанные записи. Лог размером от 256 MiB ротируется в любом случае;
непрочитанный хвост тогда учитывается как потеря. При свободном месте ниже 512 MiB (`storageLowBytes`) сбор
событий останавливается: reader пропускает порции, логирует раз в минуту,
`/status` показывает `ingestion.state="storage_low"`; после освобождения места
сбор продолжается с последнего checkpoint. При свободном месте ниже 64 MiB
(`storageFullBytes`) изменяющие ручки (PUT/DELETE draft, POST revisions/operations,
PATCH users/proxy-accounts, PUT scope) отвечают 507 `storage_full` до записи;
чтения, вход и выход работают, чтобы оператор видел состояние.
Каждое обращение к управляющей БД ограничено 3 с; чтения не ждут писателя.
Истёкший дедлайн или SQLITE_BUSY/LOCKED отвечает 503 `storage_busy` с заголовком `Retry-After: 2`. Ошибка `statfs` не
блокирует работу (считается достаточным с предупреждением в лог). Alert по
runtime down, config drift, rollback degraded, cert expiry и log gaps.
Уведомляющего внешнего канала нет; предупреждения панели не обещают
доставку при выключенном браузере. Audit в локальной SQLite не является
неизменяемым forensic-хранилищем.

## Общий контейнер

Pebble следит за процессами отдельно. Ошибка панели не должна приводить watchdog
к пересозданию всего контейнера при работающем Squid. Container-level status
не подменяет состояние каждого процесса. Upgrade общего image прерывает оба.

## Показатели обзора

GET /statistics читает агрегаты `rollups.db` (15-минутные и часовые за окно);
новых tables на каждый запрос нет, aggregation идёт фоновым rollup после ingest.
Окно [now−24h, now) определяется timestamp события, в ответе 24 часовых bucket.
requests, DENIED, logged bytes и source IP считаются только по сохранённым
завершённым записям. `observed_at` — время расчёта; свежесть источника берётся
из ingestion metadata /events. Нельзя считать calculation time доказательством
текущего чтения Squid. `retention_limited` обозначает достижение retention; тогда
полнота суток не обещается. Ошибка DB/формата возвращает 503, а не ложные нули.
HTTP403 от origin не равен Squid DENIED.

### Фильтры сохранённой истории

`GET /events` дополнительно поддерживает source_ip (точный IPv4/IPv6), destination
(регистронезависимая буквальная подстрока), method/result (точные строки), from/to
(RFC3339, полуоткрытый диапазон по времени события). Условия выполняются в SQLite
до LIMIT; cursor привязан ко всем значениям фильтров. Некорректные IP/время,
обратный диапазон и превышение длины дают400. Схема БД и retention не меняются.

`GET /events/facets` считает серверные фасеты и гистограмму за то же окно и с теми
же фильтрами и областью менеджера, что `/events`. Окно обязательно (`from`, `to`,
RFC3339), не длиннее 7 суток; `step` ∈ `1m`/`15m`/`1h`, не больше 1440 корзин.
Ответ: `allowed`/`denied`, `clients` (`id` → `name` из активного снимка, для
неописанных `id:""`, `name:null`), `methods`, `histogram` (`ceil((To-From)/step)`
корзин от старых к новым). Агрегация — SQL `GROUP BY` по колонкам и индексу `ts` в
месячных файлах `events-YYYY-MM.db`; для неописанных источников менеджера строки
группируются по `source_ip` и фильтруются по сетям области в Go (SQLite не умеет
CIDR). Cursor/Limit игнорируются. Дедлайн 5 с; ошибки параметров — 400
`invalid_filter`. Схема БД и retention не меняются.
UI переводит локальный datetime в ISO с timezone; новая фильтрация сбрасывает
пагинацию. До применения введённых полей действует предыдущий набор фильтров.

### Рабочая сводка доступа

`GET /activity?minutes=60` (15/60/1440/10080/43200) читает агрегаты `rollups.db`
с deadline2с. За [from,to) группирует источники по IP+username и проблемы
дополнительно по назначению+result. В ответе максимум10 наиболее частых групп
каждого типа, исходные totals отмечают усечение. Нет raw URL/path/body, checkpoint
paths/anchors и произвольных manager queries. Права чтения и область — как у events. Сводка содержит только публичные ingestion quality fields и
счётчики включённых клиентов из confirmed manifest. Ошибка storage даёт503, не
пустую успешную историю. Сервер не делает вывод о доступности клиента или точной
ACL по отсутствию/наличию записей. `/statistics` остаётся API суточной статистики,
но главная страница его больше не опрашивает.

## Инспектор и состояние экземпляра

`GET /api/v1/status` дополнен объектом `instance`: имя (env `KRAKEN_INSTANCE_NAME`,
иначе hostname), свободное и полное место на томе данных, и свежесть журнала —
метка времени последнего сохранённого события, последнего checkpoint и последнего
успешного apply, а также `telemetry_bytes` (размер телеметрии), `events_oldest_at`
(RFC3339 метка самого старого retained события или `null`) и
`telemetry_broken_files` (число файлов, отправленных в карантин этим процессом).
Место определяется `statfs` каталога SQLite-файла; ошибка чтения даёт `null` для
обоих полей, а не 503, чтобы остальной статус оставался полезным. Объект
`ingestion` (state: `ok`/`storage_low`/`error`, observed_at) отражает состояние
фонового сборщика событий. Свежесть журнала берётся из сохранённых данных
телеметрии, не из текущего чтения Squid: отсутствие событий не доказывает, что
трафика нет.

`GET /api/v1/inspector/*` — read-only API для панели инспектора: статистика
клиента (96 корзин по 15 мин), попадания доменов политики за 24 ч и 7 д, неописанные
источники, объяснение отказа по активной политике, влияние черновика и встроенные
шаблоны доменов. Окна считаются по `Event.Timestamp` относительно текущего времени
(часы инжектируемые для тестов). Доступ — admin и manager в своей области (`read`), анонимно 401.
В ответах нет URL path/query, credentials и вывода Squid: хост назначения
освобождён от порта, userinfo и path. Статистика и попадания доменов читают
агрегаты `rollups.db` (1–2 SQL-запроса по PK без rowid); explain и draft-impact
читают сырые события за 24 ч. denied считается по правилу `failed` из ingestion,
а не по origin 403.
