# Runbooks

Действия оператора выполняются командой `kraken` внутри контейнера. Состояние:

```sh
docker compose ps
docker exec kraken pebble services
docker exec kraken kraken status
docker exec kraken kraken check
docker exec kraken pebble logs -n 50
```

## Прокси недоступен

1. Отделить сбой сети и хоста от сбоя Squid: проверить маршрут к listener с
   клиента и `pebble services` на хосте.
2. Проверить процесс Squid, место на диске, DNS, срок сертификата прокси, firewall и
   последние ошибки в `pebble logs`.
3. Сравнить действующую ревизию в панели, LKG (`kraken status`) и отпечаток.
4. Если сбой после применения — откатить ревизию в истории и проверить реальный
   запрос.
5. Если сбой у upstream или DNS — не открывать доступ широкими правилами.
6. Записать время, ID операции, версию образа (`kraken version`).

## Панель недоступна, трафик идёт

Squid для восстановления UI не перезапускать. Проверить `pebble services`, логи
панели и место на диске. Перезапустить только панель:

```sh
docker exec kraken pebble restart control
```

Она восстановит журнал применения до приёма изменений. Если применение прервалось,
повторите запрос с тем же ключом идемпотентности или дождитесь восстановления.

Забытый пароль администратора:

```sh
docker exec -it kraken kraken password-reset --username admin
```

Команда работает и при остановленной панели; прежние сессии отзываются.

## Пользователи и сессии

```sh
docker exec kraken kraken user list
docker exec kraken kraken user disable <имя>
docker exec kraken kraken user enable <имя>
docker exec kraken kraken user role <имя> manager
docker exec kraken kraken sessions revoke --user <имя>
docker exec kraken kraken sessions revoke --yes        # все сессии
```

Блокировка и смена роли отзывают сессии пользователя. Последний включённый
администратор защищён. Каждое изменение пишет аудит с автором `cli`.

## APT или curl не скачивают

- Проверить, что приложение действительно использует прокси: `sudo`, systemd,
  контейнеры и APT могут не наследовать переменные shell.
- В журнале панели найти запрос по адресу клиента: отказ показывает причину.
- Различать: отказ прокси (403), логин прокси (407), ошибку TLS к прокси, ошибку
  сайта и ошибку подписи APT. Для HTTPS статус сайта прокси не видит.
- Проверить redirect и CDN-домены, подключение клиента, DNS прокси и время на
  клиенте.
- Не отключать проверку подписей APT и TLS ради устранения симптома.

## Применение завершилось ошибкой

- `rejected` — действующая конфигурация не менялась; исправить ошибку и применить
  заново.
- `rolled_back` — Squid вернулся к прежней ревизии; причина — в операции.
- `degraded` — новые применения заблокированы. Проверить место на диске и логи,
  перезапустить панель (`pebble restart control`) для восстановления, затем
  проверить `kraken status` и реальный запрос.
- Таймаут reload не значит «ничего не применилось»: повторять только с тем же ключом.

## Ручная правка конфига

Не править `squid.conf` в tmpfs и журнал в БД вручную: правка пропадёт при
следующем старте. Неизвестный squid.conf не импортируется как политика; нужное
изменение вносится через черновик или expert-секцию.

## Мало места на диске

- Меньше 512 MiB свободно — сбор событий останавливается
  (`ingestion.state=storage_low` в `/api/v1/status`) и продолжается с прежней позиции
  после освобождения места.
- Меньше 64 MiB — изменения отвечают `507 storage_full` до записи; чтение и вход
  работают.
- `503 storage_busy` с `Retry-After: 2` — таймаут или блокировка БД; повторить позже.

Телеметрия сама удаляет старые месячные файлы по сроку и бюджету
(`KRAKEN_EVENTS_RETENTION_DAYS`, `KRAKEN_EVENTS_BUDGET_MB`). Удалять вручную можно
только старые архивы в `backups/`; не трогать `control.sqlite3`, его `-wal` и `-shm`.
После освобождения места WAL сжимается плановым checkpoint.

## Копия данных

Онлайн-копия без остановки:

```sh
docker exec kraken kraken backup                       # /var/lib/kraken/backups/kraken-<UTC>.tar
docker cp kraken:/var/lib/kraken/backups/kraken-<UTC>.tar ./kraken-backup.tar
```

Архив содержит согласованную копию `data/control.sqlite3` (через `VACUUM INTO`, с
журналом применения и LKG), `certs/` и `data/telemetry/rollups.db`. Логи, месячные
файлы событий и производные файлы tmpfs не входят: последние пересоздаются из БД.
Архив принадлежит `kraken`, права 0600, существующий файл не перезаписывается.

Полная копия с остановкой: `docker compose stop` (с grace для штатного выхода),
скопировать том с сохранением владельцев, `docker compose start`. Она захватывает и
`log/`.

`control.sqlite3` обязателен; `rollups.db` желателен (иначе агрегаты пересобираются
из месячных файлов); месячные файлы событий — по желанию.

## Восстановление копии

1. Создать новый том и распаковать архив в `/var/lib/kraken`; владельцев и режимы
   entrypoint выставит сам.
2. Запустить совместимый образ на этом томе, не публикуя прокси в сети клиентов.
   Проверить вход, ревизию и реальный разрешённый и запрещённый запрос.
3. В копии остались прежние сессии. Для настоящего возврата отозвать их:
   `kraken sessions revoke --yes` или `kraken password-reset --username <имя>`.

## Обновление образа

1. Сделать копию (`kraken backup`) и записать текущую версию (`kraken version`).
2. Запланировать окно: обновление рвёт открытые туннели.
3. `docker compose pull && docker compose up -d`.
4. Проверить `kraken status`, вход и реальный запрос. Если панель предлагает
   служебное обновление конфигурации, выполнить `kraken service-update`.

Останавливать контейнер штатно (`docker compose stop`, `docker stop`) с grace:
Squid и панель выходят корректно. После `docker kill` `squid-start` удаляет
устаревший PID-файл, и Squid стартует нормально. Откат образа не откатывает схему
БД: использовать совместимую версию или восстановление копии.

## Сертификат истекает или скомпрометирован

- Выпущенный установкой: `kraken cert renew`, затем `docker compose restart kraken`.
- Свой: `kraken cert install panel|proxy` из stdin, затем перезапуск контейнера.
- Проверить TLS настоящим клиентом с проверкой имени. При компрометации ключа своего
  сертификата — отозвать его у издателя; при компрометации CA установки — удалить
  `certs/ca.*` и `certs/{panel,proxy}.*`, перезапустить и импортировать новый CA.
- API показывает метаданные файлов, а не сертификат, который сейчас отдаёт listener:
  после замены нужен перезапуск.
